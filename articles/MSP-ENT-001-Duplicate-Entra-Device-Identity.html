Entra device identity · 1st line fix + 2nd line prevention

“It says compliant in Intune, but they still can’t sign in”

A PC shows as Compliant in Intune. The user is still blocked from Microsoft 365 with “your device does not meet your organisation’s requirements”. In Entra ID, the machine name appears twice.

Nothing is broken. The PC has accidentally registered itself a second time, and the sign-in check is sometimes being shown the wrong one. The fix takes about five minutes — but one wrong click in the middle of it costs a rebuild, so read the red panel first.

About 5 minutes on the device 1st line — Part One 2nd line — Part Two Can un-enrol the PC if done wrong
⚠ Stop — the two things that break the PC
Both of these look like the fix.
Neither of them is.

This job is removing one of two nearly identical-looking things from the PC. Remove the other one and you take the Intune enrolment with it. There is no undo — the machine has to be rebuilt or re-enrolled.

❌ Never run this
dsregcmd /leave
It removes the Entra join — the good identity — and the Intune enrolment goes with it. This is the single fastest way to turn a five-minute job into a rebuild. It is never part of this fix.
❌ Never disconnect this
“Connected to … Azure AD”
That entry is the join. Under Access work or school you will see two entries that look much the same. Step 2 shows you exactly how to tell them apart before you click anything.
If you are not certain which entry is which
Stop and ask 2nd line. Thirty seconds of asking beats a rebuild — nobody has ever been told off for checking.

Background · Worth two minutes before you touch the PC
What is actually going on

The PC has two identities in Entra ID, not one. They were created by completely different things and only one of them is managed.

✓ The good one
Entra joined
Created byThe PC being set up and joined properly
In Intune?Yes — managed and compliant
Sign-in checkPasses
✗ The problem
Workplace joined
Created byA user adding their work account to an app
In Intune?No — and never can be
Sign-in checkFails, always
💬
Where the second one comes from
Someone signs into Edge or an Office app and accepts “Allow my organization to manage my device”, or “Stay signed in to all your apps”. It looks harmless. It creates a whole second device record that Intune does not manage and that can never be marked compliant.
At sign-in, the PC presents one of the two
Presents the Entra joined identity → ✓ Access allowed
Presents the workplace joined identity → ✗ Blocked
💡
So the fix is simply: remove the workplace join from the PC
The Intune enrolment is a completely separate thing and is not affected. You are not un-enrolling anything, you are not deleting anything from Intune, and the PC stays fully managed throughout.

Part Two · 2nd line / Intune admin

Stopping it happening in the first place

Everything above fixes one PC that already has the problem. This part stops new ones appearing, by setting a single policy value that blocks workplace join outright.

Deploy this first so the problem stops growing, then work back through the machines that already have it. Doing it the other way round means fixing a queue that is still filling up.

🛡
What it does · One registry value, nothing more
BlockAADWorkplaceJoin

The whole change is one value on Windows devices:

KeyHKLM\SOFTWARE\Policies\Microsoft\Windows\WorkplaceJoin
ValueBlockAADWorkplaceJoin
TypeREG_DWORD
Data1
  What is affected
Blocks A user adding their work account to an app and creating a workplace-joined (Entra registered) device identity — the “Allow my organization to manage my device” tick box and “Stay signed in to all your apps”.
Does not touch Entra join, hybrid join, Intune enrolment, Autopilot, or any device that is already properly joined. Machines keep working exactly as they do now.
⚠
It does NOT clean up existing duplicates
This only prevents new ones. PCs that already carry a second identity keep it until the workplace join is removed on the device — that is Part One above.
?
Decide these three before you deploy anything
Three questions first
1

Does anything here rely on Windows BYOD? Workplace join is how a personal Windows PC gets a work identity for app protection — blocking it stops that. iOS and Android app protection do not use workplace join and are unaffected. If nobody is doing Windows BYOD, there is nothing to lose.

2

Is this a shared, multi-brand tenant? If so, target a device group, not All Devices — Intune-Windows-All is the right scope. Check its membership before you assign; anything tenant-wide hits every brand in the tenant at once.

3

Check the Settings Catalog first. In Intune, Devices > Configuration > Create > Settings catalog, search workplace join. If your tenant surfaces a native setting, use it — a native setting reports compliance properly and a script does not. If nothing sensible comes back, use the script route below. Do not spend more than five minutes looking.

A
Platform script
Simplest — use this if unsure
✓ Works on any licence

Runs once per device in SYSTEM context. Good enough for a value nobody is going to change back.

Intune > Devices > Scripts and remediations > Platform scripts > Add > Windows 10 and later
SettingValue
NameBlock Entra workplace join

Enforce script signature checkNo

✎
Save as Block-WorkplaceJoin.ps1 — plain ASCII, no smart quotes
Curly quotes and em dashes pasted from a document will break the script when PowerShell reads the file. Save it as plain text.
Block-WorkplaceJoin.ps1 
# Blocks Entra (Azure AD) workplace join. Does NOT affect Entra join or Intune enrolment.
$Key   = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\WorkplaceJoin'
$Name  = 'BlockAADWorkplaceJoin'
$Value = 1

try {
    if (-not (Test-Path -LiteralPath $Key)) {
        New-Item -Path $Key -Force | Out-Null
    }
    New-ItemProperty -LiteralPath $Key -Name $Name -Value $Value -PropertyType DWord -Force | Out-Null

    # Read it back. A script that sets a value and never checks is a script that
    # reports success on a machine where nothing changed.
    $check = (Get-ItemProperty -LiteralPath $Key -Name $Name -ErrorAction Stop).$Name
    if ($check -eq $Value) {
        Write-Output "OK: $Name = $check"
        exit 0
    }
    Write-Output "FAILED: $Name = $check (expected $Value)"
    exit 1
}
catch {
    Write-Output "FAILED: $($_.Exception.Message)"
    exit 1
}

Detection script
Detect-WorkplaceJoinBlock.ps1 
$Key  = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\WorkplaceJoin'
$Name = 'BlockAADWorkplaceJoin'

try {
    $v = (Get-ItemProperty -LiteralPath $Key -Name $Name -ErrorAction Stop).$Name
    if ($v -eq 1) {
        Write-Output "Compliant: $Name = 1"
        exit 0
    }
    Write-Output "Drift: $Name = $v"
    exit 1
}
catch {
    Write-Output "Missing: $Name is not set"
    exit 1
}
ℹ
Exit codes
exit 0 means compliant and nothing runs. exit 1 triggers the remediation.
Remediation script & settings

Use the same script as Option A as the remediation script. Settings: run in SYSTEM (not logged-on credentials), 64-bit host, daily schedule.

By hand on a single device
For a machine in front of you, or testing first
Local admin needed

Same registry value, applied locally. This is a machine-wide setting, so it does not matter which user is signed in — but you do need local administrator rights.

PowerShell — fastest

Open PowerShell as Administrator and paste:

PowerShell · elevated 
$Key   = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\WorkplaceJoin'
$Name  = 'BlockAADWorkplaceJoin'

if (-not (Test-Path -LiteralPath $Key)) { New-Item -Path $Key -Force | Out-Null }

# Read it back - do not trust a set you have not verified
Get-ItemProperty -LiteralPath $Key -Name $Name

Registry Editor — if you would rather click
1

Win + R, type regedit, Yes at the prompt.

2

Navigate to HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Windows.

3

If there is no WorkplaceJoin key under Windows: right-click Windows > New > Key > name it WorkplaceJoin.

4

Right-click WorkplaceJoin > New > DWORD (32-bit) Value.

5

Name it exactly BlockAADWorkplaceJoin. Case does not matter; spelling does.

6

Double-click it, set Value data to 1. Hexadecimal or Decimal — 1 is 1 either way. OK, then close regedit.

⚠
It must be a DWORD (32-bit) Value
Not a String, not a QWORD. The wrong type is ignored silently — the value sits there looking perfectly correct and does absolutely nothing.
Undoing a manual change
PowerShell · elevated 
Remove-ItemProperty -LiteralPath 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\WorkplaceJoin' -Name 'BlockAADWorkplaceJoin' -ErrorAction SilentlyContinue

Or in regedit, right-click the value and Delete.

↻
If Intune is also pushing this
A device that gets both the Intune script and a manual edit is fine — they set the same value. But the Intune version wins the next time it runs, so undoing it by hand on a managed device is temporary. Remove the assignment as well, or it comes back.

⚠
Removing a platform script assignment does not undo it
If you used Option A, a platform script only runs forward — unassigning it leaves the value in place. You need a second script to reverse it, or do it by hand. Option B is easier to reverse: change the remediation and it corrects itself on the next run.

Appendix · 2nd line only
Cleaning up the leftover Entra object
🧹
This is tidying, not the fix
Once the workplace join is off the PC, the leftover device object presents nothing. It can be removed afterwards, but removing it is housekeeping.
🔑
Check for BitLocker keys before deleting any duplicate device object
Deleting an object destroys the recovery keys escrowed against it, and that is not recoverable. Get-DuplicateDeviceObjects.ps1 in the CE toolkit checks this for you and labels each object.

Quick answers
Questions that come up
Will removing the workplace join sign the user out of everything?

They will need to sign out of Windows and back in at the end of Step 4, and they may be asked to sign in to Office apps again afterwards. Nothing is deleted and no data is lost — the PC stays enrolled in Intune throughout.

The user has more than one work account on the PC. Which one do I remove?

The one that has no MDM sync information behind the Info button. If more than one entry fits that description, or you are not certain, escalate rather than guessing.

Can I just delete the duplicate from Entra ID and be done with it?

No. The PC re-registers within about a day if the workplace join is still on the device, so you get the same call back. Fix the device first; the cloud object is tidying afterwards, and only after the BitLocker check in the Appendix.

Does this affect iPhones and Android phones?

No. Workplace join is a Windows concept. iOS and Android app protection policies do not use it and are completely unaffected by the block in Part Two.

The block is deployed, but a machine still shows WorkplaceJoined : YES.

Expected. The block only prevents new workplace joins — it does not remove one that already exists. Work through Part One on that machine.
