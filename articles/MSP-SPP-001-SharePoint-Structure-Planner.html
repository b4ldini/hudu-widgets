Article Overview

Before a file-server-to-SharePoint migration starts, the customer needs to decide where their files should live and who should be able to see what. The SharePoint Structure Planner lets them do that themselves: a single web page where they sketch Sites → Document Libraries → Folders, add the people who need access, and group them — while a live health check nags the design into SharePoint best-practice shape. No SharePoint knowledge is needed on their side; every term is explained in plain English as they go.

This guide covers the full round trip: sending the planner to the customer, what they do with it, getting their plan back by email, loading it into the planner yourself to review, and turning the agreed plan into the migration design. The planner is embedded in the middle of this article, so you can review a returned plan without leaving the page.

The customer’s plan never reaches us automatically

The planner saves the draft in the customer’s own browser — on that machine, in that browser, only. Nothing is uploaded anywhere. Step 01 of 05
Send the Planner to the Customer
1

Email the customer the planner link: b4ldini.github.io/hudu-widgets/tools/sp-structure-builder.html. It opens in any browser with nothing to install or sign in to.

2

If the customer can’t reach external links, attach the HTML file itself instead — it’s a single self-contained file that works opened straight from their Downloads folder, even offline.

3

Tell them what we need in one line: “Sketch how you’d like your files organised after the move and who should see what — the page explains everything as you go. When you’re done, click Copy as text and paste the result into a reply to us.”

4

Point them at the built-in how-to at the top of the planner — it has a plain-English glossary (what a site, library and folder actually are) so you shouldn’t need to explain SharePoint concepts yourself.

ℹ
Aimed at non-technical people on purpose
The planner never shows raw SharePoint jargon without explaining it — filing-cabinet analogies, tooltips on every term, and guidance notes in every panel. It’s safe to hand to an office manager with no briefing call.
↓
2
Step 02 of 05
What the Customer Does (So You Can Support Them)
1

Map the structure. They click + Add a site for each broad area of the business, add document libraries inside each site, and folders inside libraries for everyday filing.

2

Add people once. The People panel is a directory — each person (name or email) is typed once, then clicked into place everywhere else as a pill. Bulk add with a comma-separated list works too.

3

Group the people. In Access groups, they build named sets of people and tick which groups can see each site or restricted library. Technical spo- group names are auto-generated — customers rarely have to invent one.

4

Follow the health check. The panel on the right flags anything against best practice — missing owners, folders that should be libraries, groups with no members — and says how to fix each one. A clean health check means a plan we can build from.

5

Their draft autosaves in the browser as they work, so they can close the tab and come back to it later on the same machine.

ℹ
Restricted folders get promoted, not permissioned
If the customer marks a folder as “only some people should see this”, the health check flags it and offers a one-click Make it a library button — because SharePoint permissions belong on whole libraries, not folders. The planner won’t let a design rely on folder-level permissions.
↓
3
Step 03 of 05
Receive the Plan Back
1

The customer clicks Copy as text under “Finished? Send it back” and pastes the result into an email to us. That’s the whole handover — no attachment needed.

2

The pasted text is a readable outline (sites, libraries, folders, owners, group membership) with a machine-readable plan-data code at the bottom between ===== PLAN DATA ===== markers. The code recreates their exact design.

3

Alternatives that also work: Download plan file saves the same outline as sharepoint-structure-plan.txt to attach, and Copy share code gives just the bare code (starts SPPLAN1.) on its own.

ℹ
The email alone is enough
Don’t ask the customer for screenshots or spreadsheets — the pasted outline carries everything, including the data block. Mangled line-wrapping from their mail client is fine; the planner copes with it when loading.
↓
4
Step 04 of 05
Load & Review the Plan Yourself
1

Scroll down to the Structure Planner embedded in this article — or open it full-screen in its own tab if you want more room.

2

Click Load a plan and paste in the customer’s entire email — signature, pleasantries and all. The planner finds and extracts the plan-data code itself. Choosing their .txt file or pasting a bare share code works the same way.

3

Their design appears exactly as they built it. Walk the structure, check the health check is clean, and sanity-check it against the real file server — missing departments and one-person access groups are the usual catches.

4

Agree any changes with the customer, make them in the planner, then Copy as text to send the revised plan back for their sign-off — same round trip in reverse.

⚠
Loading a plan replaces whatever is in the planner

The planner holds one draft per browser. If you already have a design open that you care about, click Copy share code and keep it somewhere first — then load the customer’s plan.

↓
5
Step 05 of 05
Turn the Agreed Plan Into the Migration Design
1

Each site in the plan becomes a SharePoint site, with the plan’s two-plus named owners set as site owners.

2

Each library becomes a document library, with access set at the library root using the plan’s spo- groups — inherited from the site, or the specific groups listed for a restricted library. Folders inside migrate as-is, inheriting the library’s access.

3

The ACCESS GROUPS section of the plan text is your group-creation checklist: each spo- group with its full membership list, ready to create in Entra ID / Microsoft 365.

4

Folder notes in the plan (e.g. “move contents of X here”) carry the customer’s mapping hints from the old file server — fold them into the migration mapping document.

ℹ
The plan is the design input, not an automated build
Nothing is provisioned automatically — the plan tells you what to build and who goes in which group. Provision the sites, libraries and groups following our standard SharePoint migration process.

Worth Knowing
The Best-Practice Rules Built Into the Planner
Guardrails By Design

The customer can’t easily design something we’d refuse to build

The planner encodes SharePoint permissions best practice (based on the University of Cambridge UIS guidance) directly into its health check and its data model — the usual migration design mistakes are either flagged loudly or simply impossible to express.

Enforced By The Health Check
What the customer is steered towards
  • Permissions set only at library root — restricted folders get promoted to their own library with one click
  • At least two owners named on every site
  • Group names follow the spo-<site>-<function> convention — auto-generated, so it’s the default
  • Shallow folder nesting — anything deeper than three levels is flagged for findability and path-length limits
Impossible To Express
Mistakes the tool won’t let them draw
  • Folder-level permissions — folders have no permissions field at all
  • Nested sites — sites are top-level only (related sites get linked by hubs, which we handle)
  • Broken permission inheritance and person-by-person sharing — access is only ever groups on libraries and sites
🔒
Nothing is uploaded anywhere

The planner is a single HTML file with no server behind it. The customer’s draft lives in their browser only and reaches us exclusively as the text they choose to email. There’s no account, no login, and nothing for us to secure.

If Something Goes Wrong
Troubleshooting

Common Problems & Fixes

Click any problem to expand the fix

The customer says their draft has disappeared
Drafts autosave per browser, per machine — if they switched from Chrome to Edge, moved to another computer, opened the emailed file from a different folder, or cleared browsing data, they’ll see a blank planner. If they ever sent us (or saved) a plan text or share code, Load a plan restores it exactly. Encourage customers to click Copy share code at the end of each session as a cheap backup.
Pasting the customer’s email into “Load a plan” does nothing
Make sure the paste includes the full block between the ===== PLAN DATA ===== markers — forwarding chains sometimes truncate it. Hard line-wrapping is fine; the planner strips it. If the email really is incomplete, ask the customer for the Download plan file attachment or a fresh Copy share code.
An old plan file has a different-looking data block or raw JSON
Plans from earlier versions of the tool (including raw-JSON ----- PLAN DATA ----- blocks) still load — the planner upgrades old formats automatically. Just paste or open them as normal.
“Download plan file” doesn’t download anything
Some embedded or sandboxed views block file downloads. Use Copy as text instead (it carries the same data), or open the planner full-screen in its own tab where downloads work normally.
The customer wants one folder visible to only a few people
That’s the design decision the planner exists to catch. Have them tick “only some people should see this” on the folder — the health check then offers Make it a library, which converts it to a sibling restricted library with its own auto-named spo- group. SharePoint permissions belong at library root; we don’t build folder-level permissions.
I loaded a customer plan and lost the design I was working on
The planner keeps one draft per browser, and loading replaces it. If you copied a share code of the earlier design, paste it into Load a plan to get it back. Otherwise check whether it was ever exported (sent in an email, saved as a plan file) — any of those restores it. For future reviews, grab the share code before loading anything.
